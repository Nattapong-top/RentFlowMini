# บันทึกการตัดสินใจ (Architecture Decision Records)

**สถานะ:** ใช้งานอยู่
**อัปเดตล่าสุด:** 2026-11-18
**ผู้อ่าน:** เจ้าของโปรเจ็กต์และ AI ที่ช่วยพัฒนา

บันทึกเหตุผลของการตัดสินใจที่มีผลต่อ architecture, domain, workflow, data หรือการดูแลระบบ ไม่ใช้ไฟล์นี้แทน requirement หรือข้อเท็จจริงที่ยังไม่ได้อนุมัติ
## วิธีบันทึก Decision

สร้างรายการใหม่เมื่อการตัดสินใจมีผลข้ามไฟล์/โมดูล, เปลี่ยน behavior หรือช่วยป้องกันการย้อนกลับไปสู่ทางเลือกเดิมโดยไม่รู้เหตุผล

```markdown
## ADR-001: [ชื่อการตัดสินใจ]

**วันที่:** YYYY-MM-DD
**สถานะ:** Proposed / Accepted / Deprecated / Superseded
**ผู้ตัดสินใจ:** [ชื่อหรือบทบาท]
**ขอบเขต:** [component / feature / project]

### Context
[ปัญหา ข้อจำกัด และข้อมูลที่ใช้ตัดสินใจ]

### Options Considered
- **A:** [ทางเลือก] — Pros: [ข้อดี] / Cons: [ข้อเสีย]
- **B:** [ทางเลือก] — Pros: [ข้อดี] / Cons: [ข้อเสีย]

### Decision
[สิ่งที่เลือกและเหตุผล]

### Consequences
- [ผลกระทบด้านบวก]
- [trade-off, ความเสี่ยง หรือสิ่งที่ต้องดูแล]

### Evidence / Review
[ลิงก์ไฟล์, test, issue, benchmark หรือวันที่ทบทวน]
```

## ADR-006: ค่าที่จอดรถติ๊กอย่างละรายการต่อบิล ไม่นับจำนวนคัน

**วันที่:** 2026-11-18
**สถานะ:** Accepted
**ผู้ตัดสินใจ:** เจ้าของโปรเจ็กต์
**ขอบเขต:** Billing (`CreateMonthlyBillRequest`, `BillingCalculator`, แท็บสร้างบิล)

### Context
แบบ UC-01 ฉบับแรกเริ่มกำหนดว่ามอเตอร์ไซค์คันแรกไม่คิดค่าที่จอด คันที่สองขึ้นไปคิดคันละ 100 บาท และรถยนต์คิดคันละ 500 บาท แต่โค้ดที่ทำจริงให้ผู้ใช้ติ๊ก "ค่าจอดมอเตอร์ไซค์" และ "ค่าจอดรถยนต์" ในแท็บสร้างบิลประจำเดือนได้อย่างละหนึ่งรายการ ใช้อัตราจากแท็บตั้งค่า และไม่ได้เก็บจำนวนรถไว้ที่ห้อง

### Options Considered
- **A: นับจำนวนคันตามแบบแรกเริ่ม** — Pros: คิดเงินตามจำนวนรถจริง / Cons: ต้องเก็บจำนวนรถของแต่ละห้อง เพิ่ม schema หน้าจอ และ test
- **B: ติ๊กอย่างละรายการต่อบิล** — Pros: ตรงกับโค้ดปัจจุบัน ไม่ต้องเก็บข้อมูลรถ / Cons: คิดได้สูงสุดอย่างละหนึ่งคันต่อบิล

### Decision
เลือก B เพราะใช้งานง่ายกว่า วิธีใช้:
- ห้องที่มีมอเตอร์ไซค์คันเดียว ไม่ต้องติ๊ก เพราะคันแรกไม่คิดค่าที่จอด
- ห้องที่มีมอเตอร์ไซค์คันที่สอง ติ๊กค่าจอดมอเตอร์ไซค์
- รถยนต์ใช้หลักเดียวกัน คือติ๊กเมื่อต้องคิดค่าที่จอด

### Consequences
- ไม่ต้องเก็บจำนวนรถหรือประวัติรถของห้อง
- ห้องที่ต้องคิดค่าที่จอดมากกว่าหนึ่งคันของประเภทเดียวกัน เช่น มอเตอร์ไซค์ 3 คัน หรือรถยนต์ 2 คัน จะคิดได้แค่อัตราเดียว
- แบบ UC-01 ฉบับแรกเริ่มที่นับจำนวนคันถือว่ายกเลิกแล้ว

### Evidence / Review
`Application/Billing/CreateMonthlyBillRequest.cs` (`ChargeMotorcycleParking`, `ChargeCarParking`), `Domain/Billing/BillingCalculator.cs`; ทบทวนเมื่อมีห้องที่ต้องคิดค่าที่จอดมากกว่าหนึ่งคันของประเภทเดียวกัน

## ADR-005: ไม่แยกประเภทเจ้าของอยู่เอง ให้ตั้งค่าเช่าห้องเป็น 0 บาทแทน

**วันที่:** 2026-11-18
**สถานะ:** Accepted
**ผู้ตัดสินใจ:** เจ้าของโปรเจ็กต์
**ขอบเขต:** Billing และ Rooms

### Context
แบบ UC-01 ฉบับแรกเริ่มแยกผู้ครอบครองห้องเป็นสองประเภท ผู้เช่าคิดค่าเช่า ค่าน้ำ ค่าไฟ Cable TV และค่าที่จอดรถ ส่วนเจ้าของที่อยู่เองคิดเฉพาะค่าน้ำและค่าไฟ แต่โค้ดไม่เคยมีประเภทเจ้าของ และ `CreateMonthlyBillService` ออกบิลได้เฉพาะห้องที่มีผู้เช่า

### Options Considered
- **A: เพิ่มประเภทผู้ครอบครอง** — Pros: ระบบตัดรายการที่ไม่คิดให้เอง / Cons: ต้องแก้ domain, schema, หน้าจอ และ test หลายส่วน
- **B: ใช้ข้อมูลห้องและผู้เช่าที่มีอยู่** — Pros: ไม่ต้องแก้โค้ด / Cons: ผู้ใช้ต้องตั้งค่าห้องเอง

### Decision
เลือก B เพราะง่ายกว่า ห้องที่เจ้าของอยู่เองให้ตั้งค่าดังนี้:
- เพิ่มเจ้าของเป็นผู้เช่าของห้อง เพราะระบบออกบิลได้เฉพาะห้องที่มีผู้เช่า
- ตั้งค่าเช่าห้องเป็น 0 บาท
- ติ๊กยกเว้น Cable TV ที่ห้อง
- ไม่ติ๊กค่าที่จอดรถตอนออกบิล

บิลของห้องนี้จึงเหลือค่าน้ำและค่าไฟ

### Consequences
- ไม่ต้องแก้โค้ด
- ในรายการห้อง ห้องของเจ้าของจะแสดงเป็นห้องที่มีผู้เช่า
- ถ้าผู้ใช้ลืมตั้งค่าเช่าเป็น 0 บาทหรือลืมติ๊กยกเว้น Cable TV บิลจะคิดเงินผิด
- แบบ UC-01 ฉบับแรกเริ่มที่แยกประเภทเจ้าของถือว่ายกเลิกแล้ว

### Evidence / Review
`Application/Billing/CreateMonthlyBillService.cs` ปฏิเสธห้องที่ไม่มีผู้เช่า; ทบทวนเมื่อผู้ใช้ตั้งค่าห้องของเจ้าของผิดบ่อย หรือมีห้องของเจ้าของหลายห้อง

## ADR-004: แยก logic ทั้งหมดออกจาก UI

**วันที่:** 2026-11-07
**สถานะ:** Accepted (กติกาใช้กับงานใหม่ทันที ส่วนการรื้อของเดิมยังเป็น Proposed)
**ผู้ตัดสินใจ:** เจ้าของโปรเจ็กต์
**ขอบเขต:** project (ทุกหน้าจอ)

### Context
การคำนวณเงินและกติกาธุรกิจอยู่ใน Domain และ Application แล้ว แต่ logic ของหน้าจอยังอยู่ใน TabControl เช่น การเลือกห้องที่ออกบิลได้ ข้อความเตือนตอนย้ายออก และการโหลดมิเตอร์ล่วงหน้า `MonthlyBillTabControl` ยาวราว 1,600 บรรทัด logic เหล่านี้ทดสอบได้ทางเดียวคือเปิดฟอร์มจริง และถ้าวันหน้าย้ายไปทำเว็บ จะต้องเขียนใหม่ทั้งหมด ทั้งแอปยังอยู่ในโปรเจกต์ `net10.0-windows` เดียว

### Options Considered
- **A: คงไว้แบบเดิม** — Pros: ไม่ต้องรื้อ / Cons: ย้ายไปเว็บไม่ได้ เทสต์ต้องเปิดหน้าต่าง หน้าจอยาวขึ้นเรื่อย ๆ
- **B: MVP (presenter คุยกับ view interface)** — Pros: เทสต์ได้โดยไม่เปิดฟอร์ม / Cons: ผูกกับวิธีคิดของหน้าจอแบบ WinForms ใช้กับเว็บได้ไม่ดี
- **C: Application service ที่รับข้อมูลแล้วคืนข้อมูลล้วน** — Pros: เว็บเรียก service เดียวกันได้ เทสต์ได้โดยไม่เปิดฟอร์ม / Cons: ต้องย้าย logic ออกจากหน้าจอทีละส่วน

### Decision
เลือก C งานใหม่ทุกชิ้นต้องเขียน logic ในคลาสที่ไม่อ้าง `System.Windows.Forms` และคืนผลเป็นข้อมูลล้วน รวมข้อความภาษาไทยที่ผู้ใช้เห็น หน้าจอมีหน้าที่แค่รับค่าจากผู้ใช้ เรียก service และแสดงผล ห้ามเพิ่ม logic ลงใน TabControl อีก

ของเดิมจะรื้อทีละแท็บเมื่อเจ้าของโปรเจ็กต์สั่ง แผนที่เสนอไว้:
1. ย้าย Domain, Application และ Infrastructure ไปโปรเจกต์ `RentFlow.Core` ที่เป็น `net10.0` ให้ compiler กันการอ้าง WinForms
2. ย้าย logic ของแต่ละแท็บเข้า Application โดยเริ่มจากแท็บเล็ก แล้วจบที่ `MonthlyBillTabControl`
   - ความคืบหน้า: ขั้นที่ 1 เสร็จแล้ว (PR #21); แท็บห้องพักเสร็จแล้วเมื่อ 2026-11-14 (`RoomListService`, `RoomRentInput`) ข้อความแจ้งผลสำเร็จยังอยู่ในหน้าจอ; แท็บมิเตอร์เสร็จแล้วเมื่อ 2026-11-15 (`MeterReadingEntryService`, `MeterReadingInput`, `MeterReadingSaveResult.IsUpdate`); ตอนทำแท็บบิลให้เปลี่ยนการเติมค่ามิเตอร์ไปใช้ `GetEntryDefaults` ด้วย; แท็บตั้งค่าเสร็จแล้วเมื่อ 2026-11-15 (`BillingRatesInput`, `InvoiceSettingsService`, `BackupStatusText`, `UpdateBillingSettingsService.GetCurrent/Update(BillingRateValues)`) หน้าจออ่านและบันทึกผ่าน service ทั้งหมดตามที่เจ้าของโปรเจ็กต์สั่ง; ตอนทำ `MonthlyBillTabControl` ให้แก้ ISSUE-003 (การแปลงตัวเลขเงินตามภาษาเครื่อง) ไปพร้อมกัน

### Consequences
- logic ใหม่มีเทสต์ที่ไม่ต้องเปิดฟอร์ม
- เทสต์ UI เดิมเก็บไว้เป็นตาข่ายกันพฤติกรรมเปลี่ยน ถ้าจะลดเทสต์ที่ซ้ำกันต้องขออนุมัติทีละตัว
- การรื้อแต่ละแท็บเป็น refactor ห้ามเปลี่ยนพฤติกรรม และแยก PR จากงานฟีเจอร์
- ระหว่างที่ยังรื้อไม่ครบ หน้าจอเดิมจะมีทั้งแบบเก่าและแบบใหม่ปนกัน

### Evidence / Review
ทบทวนเมื่อเริ่มรื้อแท็บแรก หรือเมื่อเริ่มทำเว็บ

## ADR-003: แก้บิลที่ยังไม่ชำระด้วยการดึงข้อมูลห้องล่าสุด และแสดงพรีวิวบิลสด

**วันที่:** 2026-11-07
**สถานะ:** Accepted
**ผู้ตัดสินใจ:** เจ้าของโปรเจ็กต์
**ขอบเขต:** Billing (`Bill`, Application service ของบิล, แท็บสร้างบิล)

### Context
กรอกค่าเช่าที่ห้องผิดแล้วออกบิลไป จะแก้ค่าเช่า ค่าน้ำ และค่าไฟในบิลไม่ได้ และออกบิลใหม่ในรอบเดิมไม่ได้ เพราะหนึ่งห้องมีบิลได้หนึ่งใบต่อรอบ การแก้ราคาที่ห้องแล้วบิลไม่เปลี่ยนไม่ใช่บั๊ก เพราะบิลเก็บ snapshot ไว้ตั้งใจให้บิลเก่าไม่เปลี่ยนเมื่อขึ้นราคา ปัญหาจริงคือไม่มีทางแก้บิลที่ยังไม่ชำระ และตอนออกบิลผู้ใช้ไม่เห็นยอดก่อนบันทึก

### Options Considered
- **A: ระบบแจ้งเองเมื่อบิลไม่ตรงกับข้อมูลห้อง** — Pros: ผู้ใช้ไม่ต้องจำว่าต้องกด / Cons: ต้องเทียบทุกครั้งที่เปิดบิล และยังไม่เห็นยอดตอนออกบิล
- **B: ปุ่ม "ดึงข้อมูลห้องใหม่" ในโหมดแก้ไขบิล** — Pros: แก้ที่ต้นทางแล้วดึงลงบิล เดือนหน้าไม่ผิดซ้ำ / Cons: ผู้ใช้ต้องกดเอง
- **C: แก้ตัวเลขในบิลตรง ๆ** — Pros: ทำง่าย / Cons: ต้นทางยังผิด เดือนหน้าผิดซ้ำ
- **D: พรีวิวบิลสด** — Pros: เห็นยอดก่อนบันทึกทุกครั้ง กันออกบิลผิดตั้งแต่ต้น / Cons: งานหน้าจอชิ้นใหญ่

### Decision
เลือก B คู่กับ D

ปุ่มดึงข้อมูลห้องใหม่:
- อยู่ในโหมดแก้ไขบิล ใช้ได้เฉพาะบิลที่ยังไม่ชำระ บิลที่ชำระแล้วต้องยกเลิกการรับชำระก่อน
- ดึงค่าเช่า สถานะยกเว้น Cable TV ของห้อง และเลขมิเตอร์ของรอบบิลนั้น
- ใช้อัตราค่าน้ำและค่าไฟเดิมในบิล ไม่ดึงอัตราใหม่
- กดปุ่มแล้วค่าลงช่องในโหมดแก้ไขและพรีวิวแสดงยอดใหม่ แต่ยังไม่บันทึก
- ตอนกดบันทึก ถามยืนยันโดยแสดงยอดเดิมเทียบยอดใหม่ ถ้าตอบ "ไม่" บิลที่บันทึกไว้ต้องไม่เปลี่ยน
- คงเลขใบแจ้งหนี้และวันที่ออกบิลเดิม แก้เฉพาะยอด

พรีวิวสด (แสดงในกล่อง "สรุปรายละเอียดบิล" หัวกล่องเปลี่ยนเป็น "สรุปรายละเอียดบิล (ร่าง ยังไม่บันทึก)"):
- ตอนออกบิล: คำนวณร่างเมื่อเลือกห้อง เปลี่ยนรอบบิล หรือเปลี่ยน checkbox ร่างไม่จองเลขใบแจ้งหนี้ แสดงว่า "จะได้เลขตอนออกบิล" และวันที่ออกบิลเป็น "-"
- หลังออกบิล: ระบบเลื่อนไปห้องถัดไปและแสดงร่างของห้องนั้นทันที ถ้าไม่เหลือห้อง กล่องยังแสดงบิลที่เพิ่งออก
- คำนวณร่างไม่ได้ เช่น ยังไม่จดมิเตอร์: ล้างกล่องเป็น "-" และแสดงเหตุผลในข้อความใต้ปุ่ม แต่หลังออกบิลข้อความใต้ปุ่มยังแสดงผลการออกบิล
- ปุ่มออกบิลคำนวณใหม่ผ่าน `CreateMonthlyBillService.Create` เสมอ ไม่ใช้ตัวเลขจากร่าง
- ตอนแก้ไขบิล: คำนวณร่างเมื่อกดดึงข้อมูลห้องใหม่และเมื่อเปลี่ยน checkbox ตอบ "ไม่" ตอนยืนยันแล้วร่างยังอยู่ ออกจากโหมดแก้ไขแล้วร่างของการแก้ไขหายไป กล่องแสดงตามห้องและรอบที่เลือกใหม่
- logic อยู่ใน `CreateMonthlyBillService.Preview` (คืนร่างหรือเหตุผล) และ `UpdateBillChargesService.Preview` (คำนวณบนสำเนา) หน้าจอแค่แสดงผล

### Consequences
- ต้องมีเทสต์คุมกรณีตอบ "ไม่" ว่าบิลที่บันทึกไว้ไม่เปลี่ยน
- ยังไม่เก็บประวัติการแก้ยอด หลังบันทึกต้องเตือนให้พิมพ์บิลใหม่ถ้าเคยพิมพ์ให้ผู้เช่าแล้ว
- logic ของพรีวิวและการดึงข้อมูลห้องต้องอยู่นอกหน้าจอตาม ADR-004
- ยังไม่ทำการยกเลิกบิล การลบบิล และการปรับค่าเช่าเฉพาะเดือนเดียว
- ลำดับงานเปลี่ยนจากแผนเดิม 3 PR: รวมปุ่มดึงข้อมูลห้องใหม่และพรีวิวทั้งสองโหมดไว้ใน PR เดียว
- ทำแล้วเมื่อ 2026-11-14: ห้ามแก้เลขมิเตอร์ของรอบที่บิลชำระแล้ว และเตือนให้เปิดบิลแล้วกดดึงข้อมูลห้องใหม่ถ้าบิลยังไม่ชำระ (ตรวจใน SaveMonthlyMeterReadingService)

### Evidence / Review
`docs/archive/room-tenant-vacancy-todo.md` หัวข้อ "กติกาการแก้บิลที่ออกผิดที่ยืนยันแล้ว"; ทบทวนเมื่อต้องเก็บประวัติการแก้ยอดหรือต้องยกเลิกบิล

## ADR-002: เลื่อนการทำรายการค่าใช้จ่ายแบบกำหนดเองและส่วนลดรายบรรทัด

**วันที่:** 2026-11-06
**สถานะ:** Proposed (เลื่อนไว้ ยังไม่ทำในเวอร์ชัน Mini)
**ผู้ตัดสินใจ:** เจ้าของโปรเจ็กต์
**ขอบเขต:** Billing (`Bill`, `BillingCalculator`, repository, UI)

### Context
บิลตอนนี้มีรายการตายตัว 6 รายการ (ค่าห้อง น้ำ ไฟ ที่จอดมอเตอร์ไซค์ ที่จอดรถ เคเบิลทีวี) และ `BillingCalculator.Calculate` รับพารามิเตอร์ 13 ตัว แนวคิดที่พิจารณาไว้สำหรับอนาคต:
- เก็บรายการค่าใช้จ่ายกลาง และเก็บราคากับกฎตามประเภทห้อง
- ตอนออกบิลคัดลอกราคาลงบรรทัดบิล (snapshot) บิลเก่าจึงไม่เปลี่ยนเมื่อขึ้นราคา
- ส่วนลดรายบรรทัดรับได้ทั้งบาทและเปอร์เซ็นต์

### Options Considered
- **A: คงรายการตายตัว 6 รายการ** — Pros: เรียบง่าย ครอบคลุมหอขนาดเล็ก ไม่ต้องแก้โค้ดที่มี test แล้ว / Cons: เพิ่มรายการใหม่ต้องแก้โค้ด
- **B: เปลี่ยนเป็น `IReadOnlyList<BillLine>` + `Discount` value object** — Pros: เพิ่มรายการได้เอง ตัดพารามิเตอร์ 13 ตัว / Cons: กระทบ `Bill`, `BillingCalculator`, repository, UI และ test หลายไฟล์

### Decision
เลือก A สำหรับเวอร์ชัน Mini เพราะรายการปัจจุบันพอสำหรับขอบเขตงาน (YAGNI) เก็บ B ไว้เป็นแนวทางเมื่อมีความต้องการจริง

### Consequences
- ถ้าวันหน้าทำ B: เก็บส่วนลดเป็น value object (`None` / `Amount` / `Percent` ตรวจช่วง 0–100) ไม่เก็บเป็น string
- หักส่วนลดจากยอดรวมของบรรทัด ไม่หักจากราคาต่อหน่วย เพราะถ้าหักจากราคาต่อหน่วย ส่วนลด 10 บาทของค่าไฟ 100 หน่วยจะกลายเป็น 1,000 บาท
- คงหลัก snapshot ราคาลงบิลแบบเดียวกับ `BillMeterSnapshot`
- ย้ายทีละขั้น: เริ่มจาก `Discount` และ `BillLine` พร้อม test ก่อน ยังไม่แตะ `Bill` เดิม

### Evidence / Review
`Domain/Billing/Bill.cs`, `Domain/Billing/BillingCalculator.cs`; ทบทวนเมื่อต้องการรายการค่าใช้จ่ายนอกเหนือ 6 รายการ

## ADR-001: ใช้ SQLite แทน SQL Server และเก็บการตั้งค่าในฐานข้อมูล

**วันที่:** 2026-11-06
**สถานะ:** Accepted
**ผู้ตัดสินใจ:** เจ้าของโปรเจ็กต์
**ขอบเขต:** project (persistence, CI, การติดตั้ง)

### Context
แอปที่รันจริงเก็บข้อมูลในหน่วยความจำ ปิดแล้วหาย ส่วนโค้ด SQL Server ไม่ได้ถูกใช้และยังไม่ครบ ใช้งานบนคอมเครื่องเดียว และไม่มีข้อมูลเก่าใน SQL Server

### Options Considered
- **A: ทำ SQL Server ต่อ** — Pros: รองรับหลายเครื่อง / Cons: ต้องติดตั้งและดูแลเซิร์ฟเวอร์ สำรองยุ่งกว่า CI ต้องใช้รหัสผ่าน
- **B: SQLite โดยคงการตั้งค่าเป็นไฟล์ JSON** — Pros: งานน้อยกว่า / Cons: ต้องสำรอง 2 ไฟล์
- **C: SQLite และย้ายการตั้งค่าเข้าฐานข้อมูล** — Pros: สำรองไฟล์เดียว ไม่ต้องติดตั้งฐานข้อมูล / Cons: ต้องนำค่าจาก `settings.json` เข้าฐานข้อมูล และไม่รองรับหลายเครื่องพร้อมกัน

### Decision
เลือก C เพราะใช้เครื่องเดียว และเจ้าของโปรเจ็กต์ต้องการสำรองไฟล์เดียว ใช้ `Microsoft.Data.Sqlite` เขียน SQL เอง ไม่ใช้ EF Core ฐานข้อมูลอยู่ที่ `%LocalAppData%\RentFlowMiniApp\rentflow.db`

### Consequences
- ไม่ต้องติดตั้งฐานข้อมูล และ CI ไม่ต้องใช้รหัสผ่าน
- ถ้าวันหน้าต้องใช้หลายเครื่องพร้อมกัน ต้องกลับมาทบทวน
- ไฟล์ฐานข้อมูลไม่เข้ารหัส ต้องระวังเมื่อเก็บไฟล์สำรองนอกเครื่อง
- ห้ามวางไฟล์ที่กำลังใช้งานในโฟลเดอร์ซิงก์คลาวด์หรือโฟลเดอร์แชร์

### Evidence / Review
`docs/archive/sqlite-migration-plan.md`; ทบทวนเมื่อจำนวนเครื่องที่ใช้เปลี่ยน
