# แผนเปลี่ยนจาก SQL Server เป็น SQLite

**วันที่จัดทำ:** 2026-11-06  
**สถานะ:** แผนและแบบตารางได้รับการอนุมัติแล้ว กำลังทำระยะ 1

## 1. สรุปสั้น ๆ

เปลี่ยนมาใช้ SQLite เพราะแอปใช้บนคอมเครื่องเดียว และไม่มีข้อมูลเก่าใน SQL Server ที่ต้องย้าย

งานนี้ไม่ใช่แค่สลับฐานข้อมูล แต่คือการทำให้แอปเก็บข้อมูลถาวรเป็นครั้งแรก เมื่อเสร็จแล้ว ปิดแอปแล้วเปิดใหม่ ข้อมูลทุกแท็บต้องอยู่ครบ และการสำรองทำจากไฟล์ฐานข้อมูลไฟล์เดียว

## 2. สภาพปัจจุบัน

| ส่วน | สถานะตอนนี้ |
|---|---|
| ห้อง ผู้เช่า มิเตอร์ บิล | อยู่ในหน่วยความจำ ปิดแอปแล้วหาย |
| การตั้งค่าราคาและข้อมูลหอพัก | เก็บในไฟล์ `%LocalAppData%\RentFlow\settings.json` |
| โค้ด SQL Server | มีอยู่แต่แอปไม่ได้ใช้ และยังไม่ครบ |
| ข้อมูลตัวอย่าง | แอปสร้างห้องและผู้เช่าสมมติทุกครั้งที่เปิด เมื่อยังไม่มีห้อง |

สิ่งที่โค้ด SQL Server ยังขาด จึงแปลงตรง ๆ ไม่ได้:

- ห้องเก็บแค่รหัสกับเลขห้อง ไม่มีค่าเช่าและสถานะยกเว้น Cable TV
- ผู้เช่าไม่มีวันเข้าอยู่ เงินประกัน และข้อมูลการย้ายออก
- บิลอ่านกลับไม่ได้ และไม่มีค่าจอดรถ Cable TV เลขใบแจ้งหนี้ และการรับชำระ
- มิเตอร์ยังไม่มีตาราง

## 3. การตัดสินใจ

| เรื่อง | ผล | สถานะ |
|---|---|---|
| จำนวนเครื่องที่ใช้ | เครื่องเดียว | ยืนยันแล้ว |
| ข้อมูลเก่าใน SQL Server | ไม่มี ไม่ต้องย้าย | ยืนยันแล้ว |
| ตำแหน่งฐานข้อมูล | `%LocalAppData%\RentFlow\rentflow.db` | ยืนยันแล้ว |
| การตั้งค่า | ย้ายเข้า SQLite เพื่อให้สำรองไฟล์เดียว | ยืนยันแล้ว |
| Package | เพิ่ม `Microsoft.Data.Sqlite` และลบ `Microsoft.Data.SqlClient` ในระยะ 7 | อนุมัติแล้ว |
| เทสต์ SQL Server 17 ตัว | ลบในระยะ 7 หลังมีเทสต์ SQLite ที่ครอบคลุมแล้ว | อนุมัติแล้ว |
| Schema | ออกแบบใหม่ทั้งหมด ตามแบบในหัวข้อ 6 | อนุมัติแล้ว |
| ข้อมูลตัวอย่าง | เอาออก แอปเริ่มจากว่าง ตามหัวข้อ 7 | ยืนยันแล้ว |
| ที่สำรองนอกเครื่อง | แฟลชไดรฟ์หรือคลาวด์ | **ยังเปิดอยู่** ตัดสินใจตอนระยะ 8 |

ห้ามวางไฟล์ฐานข้อมูลที่กำลังใช้งานในโฟลเดอร์ซิงก์คลาวด์หรือโฟลเดอร์แชร์ เพราะการซิงก์ระหว่างแอปเขียนไฟล์อาจทำให้ไฟล์เสียหาย

**ยังไม่ควรใส่ข้อมูลจริงเข้าแอปจนกว่าระยะ 8 จะเสร็จ** เพราะถ้าไฟล์เสียจะกู้คืนไม่ได้

## 4. การนำการตั้งค่าเดิมเข้าฐานข้อมูล

- นำเข้าครั้งเดียว ตอนเปิดแอปครั้งแรกหลังอัปเดต
- ไม่ลบ `settings.json` เก็บไว้เผื่อต้องย้อนกลับ แต่แอปจะไม่อ่านไฟล์นี้อีกหลังนำเข้าสำเร็จ
- ถ้าไฟล์อ่านไม่ได้ ให้ใช้ค่าเริ่มต้นและแจ้งเตือนเป็นภาษาไทย แบบเดียวกับที่แอปทำอยู่ตอนนี้ เมื่อผู้ใช้บันทึกการตั้งค่าใหม่จึงจะเก็บลงฐานข้อมูล
- บิลเก่าไม่ได้รับผลกระทบ เพราะบิลเก็บยอดเงินและอัตราน้ำไฟของตัวเอง

## 5. การสำรองข้อมูลเมื่อใช้เครื่องเดียว

ข้อมูลสำรองต้องอยู่คนละที่กับข้อมูลจริง จึงจะช่วยได้เมื่อเครื่องมีปัญหา

| ที่เก็บ | ไฟล์เสีย/ลบพลาด | ดิสก์หรือเครื่องเสีย | หมายเหตุ |
|---|---|---|---|
| โฟลเดอร์อื่นในดิสก์เดียวกัน | ✅ | ❌ | ทำอัตโนมัติได้ทุกวัน |
| ไดรฟ์ D: หรือ E: ในเครื่อง | ✅ | ขึ้นกับว่าเป็นดิสก์จริงอีกลูกหรือไม่ | อาจเป็นแค่ส่วนแบ่งของดิสก์ลูกเดียวกัน |
| แฟลชไดรฟ์หรือฮาร์ดดิสก์ภายนอก | ✅ | ✅ | ต้องเสียบไว้ตอนสำรอง และเก็บในที่ปลอดภัย |
| โฟลเดอร์ซิงก์คลาวด์ เช่น OneDrive | ✅ | ✅ | สำรองอัตโนมัติได้ แต่ข้อมูลจะขึ้นไปอยู่บนบัญชีคลาวด์ |

การวางไฟล์สำรองในโฟลเดอร์คลาวด์ปลอดภัยกว่าการวางไฟล์ที่กำลังใช้งาน เพราะไฟล์สำรองเขียนเสร็จแล้วและไม่ถูกแก้ระหว่างใช้งาน

**ข้อควรระวัง:** ไฟล์ฐานข้อมูลและไฟล์สำรองไม่ได้เข้ารหัส และมีชื่อกับเบอร์ผู้เช่าและข้อมูลบัญชีธนาคารที่ตั้งไว้ ใครได้ไฟล์ไปก็เปิดอ่านได้ ถ้าเลือกแฟลชไดรฟ์หรือคลาวด์ ต้องพิจารณาเรื่องการเข้ารหัสในระยะ 8 ด้วย

**แนวทางที่แนะนำ:** ใช้ 2 ชั้น

1. **อัตโนมัติในเครื่อง:** สำรองวันละครั้งลง `%LocalAppData%\RentFlow\Backups` เก็บ 30 ชุดล่าสุด
2. **นอกเครื่อง:** ให้ผู้ใช้เลือกโฟลเดอร์ปลายทางในหน้าตั้งค่า แอปจะคัดลอกชุดล่าสุดไปให้ และแจ้งเตือนถ้าคัดลอกไม่สำเร็จ

ข้อกำหนดของระบบสำรอง:

- ใช้คำสั่งสำรองของ SQLite ไม่คัดลอกไฟล์ตรง ๆ เพื่อให้ได้ข้อมูลที่สมบูรณ์
- มีวิธีกู้คืนที่เขียนไว้ชัดเจน และทดสอบว่ากู้คืนได้จริง

## 6. แบบตาราง

### กติการ่วม

| ชนิดข้อมูลในโค้ด | เก็บเป็น | เหตุผล |
|---|---|---|
| รหัส (`Guid`) | ข้อความ | SQLite ไม่มีชนิดนี้ |
| เงิน อัตรา และค่ามิเตอร์ (`decimal`) | ข้อความ | ทศนิยมไม่เพี้ยน และคำนวณในโค้ด C# เท่านั้น |
| วันที่และเวลา | ข้อความแบบ ISO เช่น `2026-11-06` | อ่านง่ายและเรียงได้ถูกต้อง |
| ใช่/ไม่ใช่ | ตัวเลข 0 หรือ 1 | SQLite ไม่มีชนิดนี้ |

- ใช้ตารางแบบ `STRICT` เพื่อปฏิเสธข้อมูลผิดชนิด
- เปิดการตรวจ foreign key ทุกครั้งที่เชื่อมต่อ
- ใช้ `PRAGMA user_version` เก็บเลขรุ่นของ schema
- ไม่มีตารางไหนลบแถวได้ เพราะแอปยังไม่มีการลบห้อง ผู้เช่า หรือบิล

### แบบเต็ม

```sql
CREATE TABLE Rooms (
    Id              TEXT    NOT NULL PRIMARY KEY,
    RoomNumber      TEXT    NOT NULL UNIQUE,
    MonthlyRent     TEXT    NOT NULL,
    IsCableTvExempt INTEGER NOT NULL CHECK (IsCableTvExempt IN (0, 1))
) STRICT;

CREATE TABLE Tenants (
    Id                 TEXT NOT NULL PRIMARY KEY,
    FirstName          TEXT NOT NULL,
    LastName           TEXT NOT NULL,
    PhoneNumber        TEXT NULL,
    RoomId             TEXT NULL REFERENCES Rooms (Id),
    MoveInDate         TEXT NULL,
    SecurityDeposit    TEXT NULL,
    MovedOutOn         TEXT NULL,
    MovedOutFromRoomId TEXT NULL REFERENCES Rooms (Id)
) STRICT;

-- ห้องละ 1 คน ส่วนผู้ที่ย้ายออกแล้วไม่มีห้อง จึงไม่ติดกฎนี้
CREATE UNIQUE INDEX UQ_Tenants_RoomId
    ON Tenants (RoomId)
    WHERE RoomId IS NOT NULL;

CREATE TABLE MonthlyMeterReadings (
    RoomId                   TEXT NOT NULL REFERENCES Rooms (Id),
    BillingPeriod            TEXT NOT NULL,
    PreviousWaterMeter       TEXT NOT NULL,
    CurrentWaterMeter        TEXT NOT NULL,
    PreviousElectricityMeter TEXT NOT NULL,
    CurrentElectricityMeter  TEXT NOT NULL,
    PRIMARY KEY (RoomId, BillingPeriod)
) STRICT;

CREATE TABLE Bills (
    Id                       TEXT    NOT NULL PRIMARY KEY,
    RoomId                   TEXT    NOT NULL REFERENCES Rooms (Id),
    BillingPeriod            TEXT    NOT NULL,
    InvoiceNumber            TEXT    NOT NULL,
    CreatedAt                TEXT    NOT NULL,
    DueDate                  TEXT    NOT NULL,

    RentAmount               TEXT    NOT NULL,
    WaterAmount              TEXT    NOT NULL,
    ElectricityAmount        TEXT    NOT NULL,
    MotorcycleParkingAmount  TEXT    NOT NULL,
    CarParkingAmount         TEXT    NOT NULL,
    CableTvAmount            TEXT    NOT NULL,
    TotalAmount              TEXT    NOT NULL,
    IsCableTvExempt          INTEGER NOT NULL CHECK (IsCableTvExempt IN (0, 1)),

    -- มิเตอร์และอัตราตอนออกบิล มีครบทุกค่าหรือไม่มีเลย
    PreviousWaterMeter       TEXT    NULL,
    CurrentWaterMeter        TEXT    NULL,
    PreviousElectricityMeter TEXT    NULL,
    CurrentElectricityMeter  TEXT    NULL,
    WaterRate                TEXT    NULL,
    ElectricityRate          TEXT    NULL,

    -- ผู้เช่าตอนออกบิล เก็บชื่อไว้ เพื่อให้บิลเก่าไม่เปลี่ยนเมื่อแก้ชื่อภายหลัง
    TenantId                 TEXT    NULL REFERENCES Tenants (Id),
    TenantFullName           TEXT    NULL,

    PaidOn                   TEXT    NULL,
    PaymentMethod            TEXT    NULL CHECK (PaymentMethod IN ('Cash', 'BankTransfer')),

    UNIQUE (RoomId, BillingPeriod),
    UNIQUE (BillingPeriod, InvoiceNumber),

    CHECK ((TenantId IS NULL) = (TenantFullName IS NULL)),
    CHECK ((PaidOn IS NULL) = (PaymentMethod IS NULL)),
    CHECK (
        (PreviousWaterMeter IS NULL) = (CurrentWaterMeter IS NULL)
        AND (PreviousWaterMeter IS NULL) = (PreviousElectricityMeter IS NULL)
        AND (PreviousWaterMeter IS NULL) = (CurrentElectricityMeter IS NULL)
        AND (PreviousWaterMeter IS NULL) = (WaterRate IS NULL)
        AND (PreviousWaterMeter IS NULL) = (ElectricityRate IS NULL)
    )
) STRICT;

-- มีได้แถวเดียว ถ้ายังไม่มีแถว แอปจะใช้ค่าเริ่มต้น
CREATE TABLE BillingSettings (
    Id                    INTEGER NOT NULL PRIMARY KEY CHECK (Id = 1),
    WaterRate             TEXT    NOT NULL,
    ElectricityRate       TEXT    NOT NULL,
    MotorcycleParkingRate TEXT    NOT NULL,
    CarParkingRate        TEXT    NOT NULL,
    CableTvRate           TEXT    NOT NULL
) STRICT;

CREATE TABLE InvoiceSettings (
    Id                 INTEGER NOT NULL PRIMARY KEY CHECK (Id = 1),
    PropertyName       TEXT    NOT NULL,
    Address            TEXT    NOT NULL,
    BankAccountDetails TEXT    NOT NULL
) STRICT;
```

### เหตุผลของจุดที่ควรดู

- **`DueDate` เก็บในบิล:** แม้คำนวณจากรอบบิลได้ แต่ถ้ากติกาวันครบกำหนดเปลี่ยนภายหลัง บิลเก่าต้องไม่เปลี่ยนตาม
- **การรับชำระอยู่ในตาราง `Bills`:** ตามกติกาปัจจุบัน 1 บิลรับชำระเต็มจำนวนครั้งเดียว ถ้าภายหลังมีการจ่ายบางส่วนค่อยแยกตาราง
- **`UNIQUE (BillingPeriod, InvoiceNumber)` เป็นกฎที่เพิ่มใหม่:** เลขใบแจ้งหนี้เริ่มใหม่ทุกรอบ จึงห้ามซ้ำเฉพาะในรอบเดียวกัน In-Memory ไม่ได้ตรวจกฎนี้ แต่ service สร้างเลขไม่ซ้ำอยู่แล้ว จึงเป็นการกันข้อมูลผิดพลาดเพิ่มอีกชั้น
- **ไม่มีกฎห้ามเงินติดลบในตาราง:** เงินเก็บเป็นข้อความ และ `Money` ตรวจกฎนี้ในโค้ดอยู่แล้ว

## 7. ข้อมูลตัวอย่าง

`SeedInitialData` ใน `Program.cs` สร้างห้อง 10 ห้องพร้อมผู้เช่าสมมติเมื่อยังไม่มีห้อง เมื่อมีฐานข้อมูลถาวร ข้อมูลสมมติจะถูกบันทึกลงไฟล์จริง และแอปยังไม่มีปุ่มลบห้องกับผู้เช่า

เจ้าของโครงการตัดสินใจให้เอาออก โดยแอปจะเริ่มจากว่าง และเอาออกในระยะ 6 พร้อมกับที่แอปเริ่มใช้ SQLite จริง

## 8. ลำดับงาน

แต่ละระยะแยก branch และ PR ให้ CI ตรวจก่อนเข้า `main`

| ระยะ | งาน | ผลที่ตรวจได้ | โหมด |
|---|---|---|---|
| 0 | บันทึกการตัดสินใจ และอัปเดตเอกสาร | เอกสารตรงกัน | ปกติ |
| 1 | เพิ่ม package สร้างไฟล์ฐานข้อมูล และระบบอัปเดต schema พร้อมสำรองไฟล์ก่อนอัปเดต | เปิดครั้งแรกแล้วได้ฐานข้อมูลใหม่ | เข้ม |
| 2 | เก็บห้องและผู้เช่า | เขียนแล้วอ่านกลับได้ครบทุกค่า | เข้ม |
| 3 | เก็บมิเตอร์ | บันทึกซ้ำรอบเดิมแล้วเป็นการอัปเดต | เข้ม |
| 4 | เก็บบิลครบ และเพิ่มวิธีโหลดบิลเดิมใน `Bill` | ยอดเงิน การรับชำระ และยกเว้น Cable TV อ่านกลับได้ตรงทุกหลัก | เข้ม |
| 5 | เก็บการตั้งค่า และนำค่าจาก `settings.json` เข้าฐานข้อมูล | ค่าเดิมยังอยู่ครบหลังอัปเดต | เข้ม |
| 6 | ให้แอปใช้ SQLite จริง และแสดงข้อความภาษาไทยเมื่อเปิดฐานข้อมูลไม่ได้ | ปิดแล้วเปิดใหม่ข้อมูลอยู่ครบ | เข้ม |
| 7 | ลบโค้ด SQL Server, สคริปต์, package, เทสต์ และขั้นตอนใน CI แล้วอัปเดตเอกสาร | CI ผ่านโดยไม่ต้องติดตั้งฐานข้อมูล | ปกติ |
| 8 | ระบบสำรองและกู้คืนตามหัวข้อ 5 | กู้คืนจากไฟล์สำรองได้จริง | เข้ม |

- ระยะ 1–6 และ 8 ใช้โหมดเข้ม เพราะแตะเงินและข้อมูลที่บันทึกจริง โดยแบ่งทำทีละพฤติกรรมและตรวจทานเป็นช่วง ๆ
- ลบ SQL Server ในระยะ 7 เพื่อให้ย้อนกลับได้ถ้าระหว่างทางมีปัญหา
- เทสต์ฐานข้อมูลใช้ไฟล์จริงแยกต่อเทสต์ และใช้ชุดเทสต์เดียวกับ In-Memory เพื่อให้พฤติกรรมตรงกัน
- In-Memory Repository ยังเก็บไว้ เพราะเทสต์ UI ใช้อยู่

## 9. ความเสี่ยงและวิธีรับมือ

| ความเสี่ยง | วิธีรับมือ |
|---|---|
| ทศนิยมของเงินเพี้ยน | เก็บเป็นข้อความ คำนวณในโค้ด C# เท่านั้น และมีเทสต์อ่านกลับตรงทุกหลัก |
| ลำดับการแสดงผลเปลี่ยน | เรียงผู้เช่าและห้องในโค้ด C# แบบเดียวกับ In-Memory เพราะ SQLite เรียงภาษาไทยไม่เหมือนกัน และเรียงบิลตามลำดับที่เพิ่ม |
| ข้อมูลอ้างอิงห้องที่ไม่มีอยู่ | เปิดการตรวจ foreign key อย่างชัดเจน และมีเทสต์ยืนยัน |
| ข้อความเมื่อข้อมูลซ้ำเปลี่ยนไป | แปลง error ของ SQLite ให้ได้ข้อความภาษาไทยเหมือนเดิม |
| ไฟล์ฐานข้อมูลเสียหรือถูกล็อก | ไม่สร้างไฟล์ใหม่ทับ และแสดงข้อความภาษาไทยบอกสิ่งที่ควรทำ |
| อัปเดต schema แล้วพัง | สำรองไฟล์ก่อนอัปเดต และทำในธุรกรรมเดียว |
| ไฟล์ถูกเปิดอ่านโดยผู้อื่น | เก็บในโฟลเดอร์ของผู้ใช้ Windows และเตือนเรื่องไฟล์สำรองตามหัวข้อ 5 |
| ไฟล์เทสต์ลบไม่ได้เพราะยังถูกเปิดค้าง | ล้าง connection pool หลังเทสต์ |

## 10. เกณฑ์ว่างานเสร็จ

- ปิดแล้วเปิดแอปใหม่ ข้อมูลทุกแท็บอยู่ครบ และยอดเงินตรงทุกหลัก
- การตั้งค่าเดิมถูกนำเข้าครบ
- แอปไม่ต้องติดตั้งฐานข้อมูลเพิ่ม
- ไม่เหลือโค้ด package และขั้นตอน CI ของ SQL Server
- CI ผ่านโดยไม่ต้องใช้รหัสผ่านฐานข้อมูล
- ไม่มีข้อมูลจริงหรือ secret ในโค้ด เทสต์ และเอกสาร
- สำรองและกู้คืนได้จริงตามวิธีที่เขียนไว้
- `current-code-status.md` และ `roadmap.md` ตรงกับระบบจริง
