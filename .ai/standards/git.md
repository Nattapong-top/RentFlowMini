# Git Standard

เอกสารหลักสำหรับแนวปฏิบัติร่วมกับ AI คือ `.ai/standards/ai-development-style.md`.

## ก่อนเสนอ Commit

1. หลังสร้างหรือแก้ไขไฟล์ทุกครั้ง ให้ตรวจว่าไฟล์ถูก `.gitignore` หรือไม่ด้วย `git check-ignore -v <path>` หรือวิธีที่เทียบเท่า
2. หากไฟล์ไม่ถูก `.gitignore` และอยู่ใน scope ให้ `git add -- <path>` ทันทีทุกครั้ง ห้ามรอรวมไปทำตอนท้าย
3. หากไฟล์ถูก `.gitignore` ห้าม `git add` ไฟล์นั้น ไม่ว่าจะเป็นไฟล์ที่สร้างใหม่หรือไฟล์ที่แก้ไขแล้ว และห้ามใช้ `git add -f` เพื่อหลบกฎนี้
4. ตรวจ `git status --short` และ `git diff --cached` ทุกครั้งหลัง stage เพื่อยืนยันว่าไฟล์ที่ไม่ถูก ignore ถูก stage ครบ ไฟล์ที่ถูก ignore ไม่ถูก stage และไม่มีไฟล์นอก scope ปน
5. ห้ามใช้ `git add .`, `git add -A` หรือ wildcard กว้าง ๆ เพราะอาจนำการเปลี่ยนแปลงของป๋าหรือไฟล์นอก scope เข้า staging
6. รันทดสอบที่เกี่ยวข้องตามคำสั่งที่ระบุในโปรเจ็กต์ และรายงานผลรวมถึงสิ่งที่ยังไม่ได้ทดสอบ
7. เสนอข้อความ commit ที่ชัดเจน กระชับ และตรงกับการเปลี่ยนแปลง โดยต้องสื่อพฤติกรรมที่เพิ่ม แก้ หรือลบ ไม่ใช่บอกเพียงชื่อไฟล์หรือชื่อส่วนประกอบ

## การอนุมัติและการดำเนินการ (Atomic Commits & Workflow)

- **Atomic Commits:** ให้ดำเนินการพัฒนาทีละ Task ให้เสร็จสมบูรณ์ (รวมถึงเขียนและรันเทสต์ผ่าน 100%) แล้วทำการ Commit แยกเป็นอิสระทีละเรื่องทันที เพื่อให้ประวัติ Git (Git History) สะอาด ตรวจสอบย้อนหลังง่าย และเป็นจุดเซฟที่ปลอดภัย
- ห้ามสร้าง commit, merge, push, เปิด PR หรือเปลี่ยนประวัติ Git จนกว่าป๋าจะสั่งอย่างชัดเจน
- Commit หนึ่งรายการควรมีขอบเขตเดียวและอยู่ในสถานะที่ตรวจสอบได้
- Commit message ควรบอกว่า “ระบบทำอะไรได้เพิ่มขึ้น” หรือ “พฤติกรรมใดถูกแก้ไข”
- ใช้รูปแบบ Conventional Commits เมื่อเหมาะสม เช่น `feat:`, `fix:`, `refactor:`, `test:`, `docs:` และ `chore:`
- บรรทัดแรกควรสรุปพฤติกรรมหลักให้จบในประโยคเดียว โดยไม่ใช้คำกว้างเกินไป เช่น `update code` หรือ `fix issue`
- หากมีหลายพฤติกรรมที่เกี่ยวข้องกัน ให้เพิ่มรายละเอียดใน commit body เป็นรายการสั้น ๆ
- ไม่มีคำสั่ง Git ผ่าน `make`; ใช้คำสั่ง Git ที่เหมาะสมกับ branch และสถานการณ์จริงหลังได้รับอนุมัติ
- ก่อน commit ต้องยืนยันว่าไฟล์ที่สร้างหรือแก้ไขในรอบงานซึ่งไม่ถูก ignore ถูก stage ครบทุกไฟล์ ไฟล์ที่ถูก ignore ไม่ถูก stage และไฟล์นอก scope ไม่ถูก stage

## แนวทางเขียน Commit Message

ลำดับความสำคัญของ commit message:

1. ใช้ข้อความหรือรูปแบบที่ป๋าระบุในคำสั่งรอบนั้น
2. หากป๋าไม่ได้ระบุ ให้ใช้กฎในเอกสารนี้และ Conventional Commits เมื่อเหมาะสม

ห้ามเปลี่ยนข้อความที่ป๋าระบุเองเพียงเพื่อให้ตรงกับตัวอย่างในเอกสารนี้

### โครงสร้าง

```text
<type>: <พฤติกรรมหลักที่เพิ่มหรือแก้>

<รายละเอียดเพิ่มเติม ถ้ามี>
```

### ตัวอย่างที่ควรใช้

```text
feat: calculate monthly bill and reject invalid meter readings

- calculate rent, water, electricity, and total amounts
- reject missing or decreasing meter readings
- report invalid readings with a shared Thai custom error
```

```text
fix: use repository path for SQL setup script in CI
```

### ตัวอย่างที่ควรหลีกเลี่ยง

```text
update code
fix issue
add billing
change files
```

ข้อความเหล่านี้ไม่บอกว่าระบบมีพฤติกรรมเปลี่ยนแปลงอย่างไร ทำให้ตรวจสอบประวัติย้อนหลังได้ยาก
